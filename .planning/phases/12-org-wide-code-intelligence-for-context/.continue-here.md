## Critical self-audit findings in the fix commit itself:

### 1. `.returning(CodeChunk.id)` on upsert — UNVERIFIED
`code_indexer.py:274` — Added `.returning()` to `insert().on_conflict_do_update()`. No test proves this returns an ID on the UPDATE conflict path (not just INSERT). If it doesn't, updated chunks silently disappear from `changed_chunk_ids` and delta-embed is broken. Need: integration test or at least a compiled-SQL assertion test.

### 2. Soft-delete loop is still N+1
`code_indexer.py:289-298` — Individual `UPDATE WHERE id = chunk_id` in a for-loop. Should be a single `UPDATE WHERE id IN (batch_of_ids)`. I claimed I fixed N+1 but only fixed the upsert path.

### 3. Import inside loop body
`code_indexer.py:292` — `from sqlalchemy import update` inside the for-loop. Works (Python caches) but sloppy. Move to top-level imports.

### 4. Error path missing `changed_chunk_ids` key
`code_indexer.py:400-407` — `index_workspace_repos` error fallback dict lacks `"changed_chunk_ids": []`. Worker code uses `.get("changed_chunk_ids", [])` which accidentally works, but contract is broken.

### 5. Linking bulk-fetch not actually tested
`test_linking_code.py` and `test_linking.py` — Existing tests pass by accident because mock side_effect sequence lines up with old per-row pattern. No test exercises `_bulk_lookup_source_summaries` grouping-by-type or `id.in_()` call.

### 6. Embedding bulk-load with unbounded IN clause
`embedding.py:177` — `model_cls.id.in_(source_ids)` with potentially thousands of IDs. No chunking. PostgreSQL has practical IN clause limits.

### 7. Workspace isolation test is a tautology
`test_code_chunk_isolation.py::test_two_workspaces_same_symbol_no_conflict` — Creates two Python objects with different UUIDs and asserts they're different. Proves nothing about DB uniqueness.
