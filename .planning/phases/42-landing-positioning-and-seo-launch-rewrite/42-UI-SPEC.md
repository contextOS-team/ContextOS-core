## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Hairline offsets, compact metadata gaps, tiny icon/text separation |
| sm | 8px | Source-chip internal gaps, nav/link gaps, compact stack spacing |
| md | 16px | Default card padding, mobile section gaps, CTA group spacing |
| lg | 24px | Landing card padding, hero visual chrome, section intro gaps |
| xl | 32px | Hero content spacing, proof visual spacing, grid gutters |
| 2xl | 48px | Major section rhythm, desktop CTA/visual separation |
| 3xl | 64px | Page-level spacing between major landing sections |

Exceptions: Fixed-format interactive targets may use 40px or 44px minimum height for buttons, mobile menu controls, play controls, and touch targets. These are accessibility exceptions and remain multiples of 4.

## Typography

Declare exactly four size roles and two weights.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.55 |
| Label | 12px | 600 | 1.3 |
| Heading | 32px | 600 | 1.2 |
| Display | 64px | 600 | 1.05 |

Rules:
- Use 400 for body and support copy.
- Use 600 for labels, buttons, headings, product-card titles, and display copy.
- Do not introduce additional weights for emphasis.
- Avoid negative letter spacing. Mono labels may use uppercase tracking, but body and heading copy must keep letter spacing at 0.
- Hero display can scale down responsively with existing Tailwind breakpoints, but the type hierarchy must stay within these four roles.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | #0A0A0F | Landing background, hero canvas, product-proof browser frame, deep negative space |
| Secondary (30%) | #0F0F18 | Cards, Decision Receipt surface, source panels, integration tiles, booking shell |
| Accent (10%) | #49D6B5 | Primary CTA, section labels, verified status, active/focus rings, key graph edges, connected/live dots, selected source chips |
| Destructive | #EF4444 | Error states and destructive confirmations only |

Accent reserved for: primary CTA, hero badge dot, verified status, source evidence selection, graph connection emphasis, focus rings, section labels, and live/connected indicators.

Accent must not be used for every link, every hover state, or decorative page-wide glow. Ambient teal glows may remain subtle, but the product proof must carry the visual hierarchy.

Supporting integration colors may be used inside integration logos or source chips only: Linear, Slack, GitHub, GitLab, Jira, Notion, Telegram, and Fathom. They should never become page-level accents.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | See your decision graph |
| Secondary CTA | View a sample trail |
| Empty state heading | No decision trail yet |
| Empty state body | Connect Slack, GitHub/GitLab, Jira/Linear, docs, and meetings to build a source-backed decision graph from your team's recent work. |
| Error state | We could not load this decision trail. Refresh the page or open the booking section to see ContextOS with your own workspace. |
| Destructive confirmation | No destructive actions in this phase. |

Additional copy rules:
- Use concrete verbs: finds, links, shows, explains, flags, maps, puts context into.
- Avoid generic category language in the hero: `AI search`, `chat with your docs`, `company brain`, `AI-native OS`, `self-improving company`, `unlock`, and `supercharge`.
- Replace unsupported metrics such as `2-6 hours` unless backed by customer evidence.
- Keep action-layer language future-tense with `coming next`, `next`, or `roadmap`.
- Every major claim must be paired with a visible product proof: source chip, integration, receipt field, graph relation, or verification state.

## Component Contracts

| Component | Contract |
|-----------|----------|
| Decision Receipt | Custom landing component. Required fields: decision title, why/rationale, people involved, original sources, affected systems/workstreams, related ticket/PR/doc, and verification state. Radius 12px max. No nested cards inside the receipt. |
| Source Evidence Chip | Clickable-looking pill with service name, source type, count or identifier, and optional timestamp. Examples: `Slack thread - 14 messages`, `Meeting - 32 min`, `PR #418`, `Linear ENG-217`, `Architecture doc`. |
| Decision Graph Preview | 4-6 understandable nodes only: decision, person, source, system, ticket/PR/doc. Keep edges sparse and readable. Do not use a large decorative network. |
| Before/After Proof | Before shows lost rationale across Slack search, stale docs, unclear PR history, and repeated questions. After shows a source-backed receipt with decision, why, sources, and affected systems. |
| CTA Buttons | Primary uses accent fill and dark text. Secondary uses transparent/dark surface with border and clear label. Both must have focus-visible rings and at least 40px height. |
| Integration Trust Bar | Must include only supported integrations shown on the page. If GitLab and Fathom appear in the integration grid, either include them in TrustBar or avoid count-based claims. |
| Booking Section | Keep Cal.com embed. Surrounding copy should promise a useful artifact: seeing the buyer's decision graph, not a generic sales demo. |

## Registry Safety

| Registry | Blocks Used | Safety Gate |
|----------|-------------|-------------|
| shadcn official | button, card, input, label, dropdown-menu, switch, skeleton, sonner, alert-dialog | not required |
| No third-party registry code | none | PASS - 21st.dev may be used as visual reference only; any future 21st.dev block must be named, inspected with shadcn registry output, and recorded before installation |

Third-party policy:
- 21st.dev is allowed for reference and future named supporting blocks, but this UI-SPEC approves no 21st.dev code by default.
- If implementation selects a 21st.dev block, record the exact registry URL, run the registry view/diff check, scan for network calls, environment access, dynamic code execution, external dynamic imports, and obfuscated source, then update this table before planning or execution depends on it.
- Do not install full-page templates from a third-party registry for this phase. The Decision Receipt is product-specific and must be custom.
